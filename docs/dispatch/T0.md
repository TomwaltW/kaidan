# 任务 T0 — 契约与骨架

## 工作区
主分支 main，直接在仓库根目录工作，不开 worktree。
如果还不是 git 仓库，先执行：
git init -b main && git add -A && git commit -m "chore: 启动包"
然后确认 `git status --short` 输出为空。

## 先读
docs/dev-spec-2026-09-18.md —— 本轮唯一权威文档。重点读：第 2 节全部、第 3 节、附录 A、B、F、G；以及根目录 CLAUDE.md 的硬规则。

## 目标
把第 3 节的契约落成可编译、可测试的 monorepo 骨架：依赖一次装齐并冻结；所有跨任务接口都有"能 import、调用即 NOT_IMPLEMENTED"的桩；验收用例 tests/e2e 写好且能跑（红的）；组装 buildApp 与 CLI 写好；最后打 tag baseline-t0 并创建 .contracts.lock。

具体：
1. 根配置：package.json（脚本与 engines 见附录 A）、pnpm-workspace.yaml（packages/*、apps/*）、tsconfig.base.json（见附录 A）、.nvmrc（24）、.npmrc（可为空）、.env.example（KAIDAN_LLM_API_KEY、FEISHU_APP_ID、FEISHU_APP_SECRET）。.gitignore 已存在，可按需补充。
2. packages/contracts：src/ 下源码已预置，一个字符都不要改。补 package.json、tsconfig.json，写 test/contracts.test.ts（≥ 8 个用例）：mini.json 能被 RomDataset 解析；config/demo.mock.yaml 与 config/tenant.example.yaml 能被 loadConfig 解析且相对路径变成绝对路径；config/mapping.example.yaml 能被 BitableMapping 解析；SKILL_NAMES 长度为 7；formatToolResultForModel 两种输出；附录 B 的每一行都能通过 SkillFrontmatter、非法 name 会失败；KaidanError 的 code 与 retryable；loadConfig 在 adapter.kind=mock 但缺 adapter.mock 时报 CONFIG（用临时文件）。
3. 按附录 A 为 adapters、tools、mcp-server、governance、agent、skills、eval、surface-feishu 与 apps/kaidan 创建 package.json、tsconfig.json；装齐依赖，生成并提交 pnpm-lock.yaml。
4. 每个包写 src/index.ts 桩：按第 3.2 节"各包必须导出的符号"表导出全部符号，类型标注为对应工厂类型，函数体调用 notImplemented("<包名>.<函数名>")。例外：@kaidan/skills 的 SKILLS_DIR 要真实实现（= 包根目录下 skills/ 的绝对路径，用 import.meta.url 计算），并创建 packages/skills/skills/ 下 7 个子目录（名字 = SKILL_NAMES，各放 .gitkeep，不写 SKILL.md）。另建脚本入口桩：packages/skills/src/lint.ts、packages/eval/src/gen.ts、validate.ts、bench.ts、packages/mcp-server/src/bin.ts（运行时向 stderr 打印"尚未实现"并以退出码 1 结束）；以及 packages/eval/fixtures/.gitkeep、packages/eval/tasks/.gitkeep、各包 test/.gitkeep、deploy/.gitkeep。
5. apps/kaidan：src/app.ts 按附录 F 实现 buildApp（真实组装代码，只调用各包工厂）；src/cli.ts 按附录 F 实现 doctor / chat / serve / mcp 四个子命令（参数解析用 node:util 的 parseArgs）；src/index.ts 导出 buildApp。
6. tests/e2e：harness.ts（第 2.2 节"公共前提"，含可前进的时钟、记录型 fake LarkClientLike、按 openId 取 Actor 的帮助函数、解析工具消息的帮助函数）+ b1-brief、b2-manager、b3-post-meeting、b4-permission、b5-approval、b6-feishu 六个 .test.ts，把第 2.2 节 B1–B6 的每一条期望都写成断言。需要的 vitest 配置放在 tests/e2e/ 内（根脚本为 vitest run --root tests/e2e）。
7. 跑验收：1–4 必须全绿；5、6 必须能执行（红的可以）。
8. 提交、创建 .contracts.lock、打 tag（见"完成后"）。

## 不要做的事
除 buildApp、CLI、SKILLS_DIR、契约测试、e2e 用例之外，不实现任何业务逻辑。T0 的产出是"类型检查通过、e2e 全红"的骨架。越界写了实现，T1–T4 的 worktree 会和你冲突。

## 验收（自己跑）
1. `pnpm install --frozen-lockfile` → 退出码 0
2. `pnpm typecheck` → 退出码 0（10 个包）
3. `pnpm test` → 退出码 0
4. `pnpm --filter @kaidan/contracts test` → ≥ 8 passed
5. `pnpm test:e2e` → 能执行，6 个用例文件都被收集；失败原因应为 NOT_IMPLEMENTED，不能是 Cannot find module 或语法错误
6. `pnpm kaidan doctor --config config/demo.mock.yaml` → 能执行到加载组件这一步（报 NOT_IMPLEMENTED 可以，报命令不存在不行）
7. 第 3.4 节归属表中出现的目录全部实际存在
