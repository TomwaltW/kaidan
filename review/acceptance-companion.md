## 怎么用

真机排错最贵的成本是「来回」——一轮没抓到日志就得从头再来一遍。所以：

- **`serve` 的日志全部写 stderr**，不要让它滚没了。开跑前就重定向下来：

  ```bash
  cd /Users/shensikai/Documents/Projects/Kaidan/kaidan
  export KAIDAN_LLM_API_KEY=… FEISHU_APP_ID=cli_… FEISHU_APP_SECRET=…
  pnpm -s kaidan serve --config ../local-config/tenant.feishu-test.yaml 2>&1 | tee /tmp/kaidan-serve-$(date +%H%M).log
  ```

- **任何一项不过，先抓齐三样再往下走**：① 日志里带 `[surface-feishu]` / `[lark]` 的那几行（含飞书返回的
  `code` / `msg`，SDK 还会带 `log_id`——提工单时飞书只认这个）；② 多维表格里那条记录**当时**的样子（截图，
  含「最后更新时间」列）；③ 你实际发的那句话的原文。
- **`log_id` 在哪**：飞书 SDK 的报错对象里带 `log_id`，会跟着 `[lark]` 或异常堆栈一起打出来。
  日志里 `grep -i log_id` 一遍；`grep -nE '\[surface-feishu\]|\[lark\]|code|log_id'` 是通用的第一刀。
- **提案与审计留在 SQLite 里**（`governance.dbPath`，测试配置是 `.data/feishu-test.db`）：
  表 `proposals`（`id / status / decided_by / decided_at`）与 `audit`。卡片上看不出来的状态，去这里查。

### 第 1 项 · 私聊 `/晨报`，收到晨报卡片，页脚有「内容由 AI 生成 · 模型名」

|---|---|
| **具体怎么做** | **销售 A**，在**与机器人的私聊**里发 `/晨报`。注意：真实时间下表里可能今天没有日程，**先把测试数据里的日程日期改到今天**，否则「今天没有日程」是数据问题不是 bug |
| **通过长什么样** | **屏幕**：一张卡片，有今日日程 / 近期要成交 / 风险商机，最后一行 `内容由 AI 生成 · 阿里云百炼 通义千问`。**日志**：`[surface-feishu]` 无报错；若出现 `agent.run 失败` 或 `处理消息失败` 即为不过 |
| **不过的时候抓什么** | ① 完全没反应 → 日志里有没有**任何**一行提到这条消息？<br>　· 有 `未开通用户发来消息：open_id=ou_…` → 不是本项的问题，是第 8 项的情形，把 open_id 填进 `users` 重启<br>　· 一行都没有 → **事件根本没到**：查应用是否已发版、可用范围、事件订阅是否选了长连接 + `im.message.receive_v1`<br>② 有反应但回「处理出错了，请稍后重试」→ 抓 `agent.run 失败 <message_id> <错误>` 那一整段堆栈<br>③ 回「模型服务配置有误 / 暂时不可用」→ 是模型不是飞书，查 `KAIDAN_LLM_API_KEY`<br>④ 卡片发不出去 → 抓 `发送卡片失败：飞书返回 <code> <msg>`（`code` 是飞书错误码）与同段的 `log_id`<br>⑤ 卡片发出来了但**排版是乱的 / 显示异常** → 这是卡片 JSON 2.0 的问题，把**卡片原文**留下（见对照表）<br>⑥ 内容不对（数字错、读不到商机）→ 复制**模型给的数字**和**多维表格里的真值**各一份；若日志里有 `… 无法转换为 ROM，已跳过` 或 `… 的阶段「X」不在 stageMap 中`，那是 `mapping.yaml` 的字段名 / 阶段名没对上 |

### 第 2 项 · 私聊 `/会后 …`，收到回复卡 + 审批卡，审批卡列出「原值 → 新值」

| | |
|---|---|
| **具体怎么做** | **销售 A** 私聊发一句大白话，主语用**表里真实存在**的客户名：`/会后 今天和 XX 开会，对方确认方案，下周三前给报价` |
| **通过长什么样** | **屏幕**：**两张**卡片——先一张回复卡（纪要 + 页脚公示），再一张标题为 **`待确认的 CRM 更新`** 的审批卡，卡上逐行列「字段：原值 → 新值」，底部两个按钮（同意 / 拒绝）。**日志**：无报错 |
| **不过的时候抓什么** | ① **只有回复卡、没有审批卡**（最可能的失败）→ 先分清是「模型没调工具」还是「卡片没发出去」：查 `.data/feishu-test.db` 的 `proposals` 表有没有新行（`SELECT id,status,created_at FROM proposals ORDER BY seq DESC LIMIT 5;`）。<br>　· **没有新行 = 模型没生成提案**，不是飞书的锅。这是**已知残余风险**（CLI 上写入类最近一轮 12/12，但单轮有抖动）。把**你发的原话**记下来——真机的价值就在于收集客户自己的说法<br>　· **有新行但没卡片 = 发送失败**，抓 `发送卡片失败：飞书返回 <code> <msg>` + `log_id`<br>② 审批卡出来了但**没有按钮 / 按钮点不动** → 卡片 JSON 2.0 的 `behaviors: callback` 问题，把卡片原文留下（对照表里「按钮 value 形状」那行）<br>③ 「原值」显示成空但表里明明有值 → 读取侧字段映射问题，记下该字段在多维表格里的**字段类型**（人员 / 关联 / 日期 / 单选）<br>④ 两张卡片顺序颠倒或只发了一张 → 记下 message_id 顺序 |
| **大概率是谁的锅** | 没生成提案 → 不是代码，是 `packages/skills/skills/post-meeting/SKILL.md` 正文 + 模型<br>卡片形状 / 按钮 / 发送 → `packages/surface-feishu/src/cards.ts`、`lark-client.ts`<br>原值读错 → `packages/adapters/src/bitable/convert.ts` + `mapping.feishu-test.yaml` |

### 第 3 项 · 点「同意」：卡片变为「已写入 CRM」，多维表格里对应记录已更新；再点一次不会重复写

> **本项是整套验收里未真机点最密集的一项**（回调注册、空响应换卡、按钮 value、`message.patch`、
> 多维表格的三种写入形状全在这里）。出问题的概率最高，**抓证据要最狠**。

| | |
|---|---|
| **具体怎么做** | 销售 A 点审批卡上的**同意**。等卡片变化后，**去多维表格里核对那条记录**（字段值 + 最后更新时间）。然后**在同一张卡上再点一次同意** |
| **通过长什么样** | **屏幕**：原卡片被替换成一张只写 **`已写入 CRM`** 的卡；多维表格里目标字段已变成「新值」，新建待办那条也出现了。再点一次 → 仍显示 `已写入 CRM`，**多维表格里的「最后更新时间」不再变化**。**日志**：无 `处理卡片回调失败` |
| **不过的时候抓什么** | ① **点了完全没反应**（卡片不变）→ 这是回调根本没到，或者回调解析失败。抓：<br>　· 日志里有没有 `处理卡片回调失败 <proposalId> <错误>`；**一行都没有**说明事件没进来 → 查回调是否选了长连接 + `card.action.trigger`<br>　· 有这行但 `<proposalId>` 是 `undefined` → **按钮 value 的回传形状不对**（对照表）<br>　· 查 `proposals` 表：`status` 还是不是 `pending`？是 `pending` → 根本没执行；变成 `failed` → 执行了但写入失败<br>② **卡片变成「操作失败，请稍后重试」** → `proposals` 表那行的状态 + `audit` 表最近几条；日志里找 `写入失败：…`，把飞书返回的 `code` / `msg` / `log_id` 抄下来<br>③ **卡片变成「已写入 CRM」但多维表格没变** → 最阴的一种。抓：该记录的 `record_id`、目标字段的**字段类型**、写入的值。人员 / 关联 / 日期三类字段的写入形状（`[{id}]` / `["rec…"]` / 毫秒时间戳）全是未真机项<br>④ **新建的待办没出现** → 同上，看 `create` 而不是 `update`；关联字段 `opportunityId` 的写入形状是重点<br>⑤ **卡片没被替换但内容其实处理了** → `im.v1.message.patch`（换卡）的问题，抓 `更新卡片失败：飞书返回 <code> <msg>`<br>⑥ **再点一次真的写了第二遍**（最后更新时间又变了）→ 幂等失效，抄下 `proposals` 表那行的 `status` 和两次的时间戳 |
| **大概率是谁的锅** | 回调收不到 / 解析不出 / 换卡失败 → `packages/surface-feishu/src/**`（`surface.ts` 的 `onCardAction`、`parse.ts`、`lark-client.ts` 的 `updateCard`）<br>写入形状 / 写不进去 → `packages/adapters/src/bitable/**`（`api.ts` 的 `create`/`update`、`convert.ts` 的 `toBitable`）<br>幂等 / 状态机 → `packages/governance/src/index.ts`（`approve` 里 `if (p.status === "committed") return p;`） |

### 第 4 项 · 点「拒绝」：卡片变为「已拒绝」，多维表格无变化

| | |
|---|---|
| **具体怎么做** | 重新触发一次 `/会后` 拿到新的审批卡（**别复用第 3 项那张已 committed 的**），点**拒绝**。然后去多维表格核对那条记录**没有变** |
| **通过长什么样** | **屏幕**：卡片变成 `已拒绝`。**多维表格**：目标字段原样，最后更新时间未变。**DB**：`proposals` 那行 `status = rejected`，`decided_by` 是销售 A 的 open_id |
| **不过的时候抓什么** | ① 点了没反应 → 与第 3 项①同一套（回调 / value 形状）<br>② 变成「已拒绝」但表里**变了** → 严重问题，抄下记录的前后值 + 最后更新时间 + `audit` 表最近 5 条<br>③ 变成「该提案已处理过，不能再次操作」→ 你点的是同一张已处理的卡，重来一次<br>④ 拒绝后过一会儿又被写进去了 → 查是不是另一条 pending 提案被别人点了（`proposals` 表按 `seq` 倒序看） |
| **大概率是谁的锅** | 回调链路 → `packages/surface-feishu/src/**`；状态机 → `packages/governance/src/index.ts`（`reject`） |

### 第 5 项 · 先在多维表格里手动改同一字段，再点「同意」：提示「记录已被他人修改，请重新生成」

| | |
|---|---|
| **具体怎么做** | ① 触发 `/会后` 拿到审批卡，**先别点**；② 去多维表格里，把**提案要改的那个字段**（卡上写着「原值 → 新值」的那个，比如「阶段」）**手动改成第三个值**（既不是原值也不是新值）；③ 回飞书点**同意** |
| **通过长什么样** | 卡片变成 **`记录已被他人修改，请重新生成`**。多维表格保持你手改的那个值，**没有被覆盖**。DB 里 `proposals` 那行 `status = failed` |
| **不过的时候抓什么** | ① **直接写进去了、覆盖了你的手改** → 冲突检查失效，这是本项唯一真正的失败。抓：手改成什么、提案的「原值 → 新值」、最终表里是什么、该记录的 `record_id`<br>② **明明没手改却报「记录已被他人修改」**（误报）→ 更常见，说明**读回来的值和提案里记的原值形状不一致**。冲突判定是「逐字段比较提案的 `before` 与当前读回的值」（`findConflict`，`packages/governance/src/index.ts:361`），差一点点形状就会误报。抓：<br>　· 错误文案括号里的 **`字段已变化：<字段名>`**——它直接点名了是哪个字段<br>　· 那个字段在多维表格里的**类型**（人员 / 关联 / 日期最容易；日期是毫秒 vs ISO 字符串、人员是 `[{id}]` vs 字符串）<br>　· 提案卡上显示的「原值」原文<br>③ 报「目标记录已不存在」→ 你手改时把行删了，或 `record_id` 变了 |
| **大概率是谁的锅** | 误报（形状不一致）→ `packages/adapters/src/bitable/convert.ts` 的 `fromBitable`（读回来的形状）<br>不报（覆盖了）→ `packages/governance/src/index.ts` 的 `findConflict` |

### 第 6 项 · 销售 A 询问销售 B 的商机：回复「无权限」，不泄露任何字段

| | |
|---|---|
| **具体怎么做** | 先在多维表格里确认**有一条商机的负责人不是销售 A**（比如挂在主管或另一个人名下），记下它的客户名。然后**销售 A** 私聊问：`XX公司那个单子现在什么阶段了？金额多少？` |
| **通过长什么样** | 回复大意是查不到 / 无权限，**且正文里不出现那条商机的任何字段值**——没有金额、没有阶段、没有联系人、没有预计成交日期。工具层给模型的原文是 `无权限访问该记录` |
| **不过的时候抓什么** | ① **泄露了任何一个字段值** → 这是**最严重的一类失败，立刻停下记全**：你问的原话、完整回复原文、那条商机在表里的真实值、`--as` 对应的 open_id、该商机负责人字段的**原始内容**（截图，看清是人员类型还是文本）<br>② 回复的是「处理出错了」而不是无权限 → 抓 `agent.run 失败` 堆栈<br>③ **反过来**：销售 A 问**自己的**商机也被拒 → 说明负责人字段没匹配上他的 open_id。抓该记录负责人字段的原始值 + 配置里销售 A 的 `openId`，两者要能对上（人员字段回来的是 `[{id: "ou_…"}]`） |
| **大概率是谁的锅** | 可见性判定 → `packages/adapters/src/query.ts`（`DENIED_MESSAGE`）+ `packages/tools/src/index.ts`<br>负责人字段读不对 → `packages/adapters/src/bitable/convert.ts`（人员字段形状）+ `mapping.feishu-test.yaml` 里各表的 `ownerId` 映射（样例里映射到「负责人」字段） |

### 第 7 项 · 群里不 @ 机器人不响应；@ 机器人正常响应

| | |
|---|---|
| **具体怎么做** | 建一个测试群，**把机器人拉进群**，三个测试账号都在群里。① 销售 A 在群里发一句不带 @ 的话（`今天几点开会`）；② 再发一句 `@开单助手 /晨报` |
| **通过长什么样** | ① 机器人**一点反应都没有**（日志里也不该有 `agent.run` 相关的行）；② @ 之后正常回卡片 |
| **不过的时候抓什么** | ① **不 @ 也回了**（最该抓的方向，群里刷屏会直接毁掉试点）→ 抓那条消息原文 + 日志时间戳。判定在 `surface.ts:131`：`if (msg.chatType === "group" && !msg.mentionedBot) return;`——要么 `chatType` 没解析成 `group`，要么 `mentionedBot` 误判成 true<br>② **@ 了也不回** → 分两种：<br>　· 日志里**一行都没有** → 权限问题，查是否开通「接收群聊中 @机器人消息事件」（`im:message.group_at_msg:readonly`），改完要**重新发版**<br>　· 日志里有消息进来但没后续 → `mentionedBot` 判成了 false。**这通常是机器人自己的 open_id 取错了**（启动时用 `bot/v3/info` 取的，见对照表）。抓：日志里启动那一段有没有 `获取机器人信息失败` |
| **大概率是谁的锅** | `packages/surface-feishu/src/parse.ts`（`mentions` 解析）+ `surface.ts:131`；open_id 取错 → `lark-client.ts` 的 `fetchBotOpenId` |

### 第 8 项 · 不在配置名单里的人私聊：收到「你还没有开通开单助手」

| | |
|---|---|
