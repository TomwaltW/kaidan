## 4. 仍然失败 / 不稳定（按风险排序）

> **2026-09-20 下午更正**：本节第 1 条当时判断「提示词层面的边际收益不大」——这个判断**是错的**。
> T7 用一轮更狠的正文改写（正例 / 反例 + 「先调工具再写回复」前置）把写入类做到了 12/12，见第 7 节。

1. **提案类只有大约 45% 的成功率**（三次样本合计 4/9，见第 2 节第 3 轮表）。改前是 0/4「完全不调写入工具」，改后变成「有时调、有时只在文字里描述」。`write-04`（/商机体检 后补 nextStep）两次都失败，是最稳定的失败项。**这是目前离试点最远的一项**：销售说了「帮我更新到 CRM」，一半的概率什么都没发生。提示词已经写到「必做、要带工具返回的提案 id、没提案不许写那句话」，再往上加措辞的边际收益不大，下一步应该换模型比对（见第 6 节），必要时在 runtime 里对「用户明确要求写入却没有产生提案」的情况做一次补救性追问。
2. **模型会编聚合数字，并声称来自工具。** 第 2 轮 `agg-06`（王经理问团队总金额）回答「2,845.6 万元」，还写了「`pipeline_snapshot`（scope=team）返回未关闭商机总金额为 28456000 元」。实际团队未关闭总额是 **6,062 万元**（张三 1868 万 + 李四 2517 万 + 赵六 1677 万），而 28,456,000 这个数在工具返回里**根本不存在**（各阶段分别是 1931 / 1766 / 1446 / 919 万）。第 1、3 轮同一题都通过 → 三次里错一次。技能正文已经写了「直接引用工具返回值」，这类错误提示词兜不住，属于模型能力问题：**选型时应当把「聚合数字是否照抄工具返回」当成一票否决项**。
3. **完成时态的措辞**：`write-02` 的回复第一句是「已将…预计成交日期从 2026-09-25 更新为 2026-10-31」，容易让销售以为已经写进 CRM（实际还要点同意）。下一轮把「已…」这类措辞在正文里禁掉。
4. 20 道题、单样本，整体分数的置信区间不窄；选型至少要每个模型跑两轮。

## 5. 其他发现（与技能无关）

- `printf '…' | pnpm kaidan chat …` 这种**管道输入**，最后会打印「错误：readline was closed」并以退出码 1 结束。交互式使用不受影响，但录演示脚本 / 写自动化时会被绊到。修的话在 `apps/kaidan/src/cli.ts` 的 chat 循环里吞掉 readline 关闭后的 prompt。
- 评测报告里不含模型回复原文（设计如此，避免 CRM 正文落盘）。复现失败任务只能另外用 `chat` 跑一遍同样的输入。
- `pnpm bench` 支持 `--only <id,id,…>`，复测单题很快。
