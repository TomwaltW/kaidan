> 用途：约访谈时先发一段 3–5 分钟的录屏，或视频会里现场敲。对象是**销售负责人 / 销售总监**，不是工程师。

## 0. 一句话结构

三幕，一条主线：**看数据 → 出提案 → 人点同意才写入**。

| 幕 | 敲什么 | 想让对方记住的一句话 |
|---|---|---|
| 1 | `/晨报` | 数字全部来自你自己的 CRM，不是模型编的 |
| 2 | `/会后 …` | AI 只能提案，写不进去 |
| 3 | `:approve <提案 id>` | 谁批的、批了什么，全留痕 |

全程 5 分钟以内。**不要临场加演**——加什么都可能是没跑过的路径。

## 1. 开录前的准备

### 1.1 一条命令把环境准备好

```bash
cd /Users/shensikai/Documents/Projects/Kaidan/kaidan
export KAIDAN_LLM_API_KEY=<百炼 API Key>        # 百炼控制台 → API-KEY；不要出现在画面里
CFG=/Users/shensikai/Documents/Projects/Kaidan/local-config/demo.qwen.yaml
```

- **密钥别进画面**：`export` 这一行在开录之前敲完，或者写在一个 `.env` 里 `source` 进来。
  录屏开始后不要再 `echo $KAIDAN_LLM_API_KEY`，也不要 `cat` 那个配置目录。
- 配置用绝对路径 `/Users/shensikai/Documents/Projects/Kaidan/local-config/demo.qwen.yaml`
  （它不在 git 里；`adapter.kind: mock`，指向仓库里的虚构数据集）。

### 1.2 开录的第一条命令（整场只启动一次）

```bash
pnpm -s kaidan chat --config $CFG --as ou_rep_zhang --now 2026-09-21T09:00:00+08:00
```

启动后屏幕上是：

```
开单助手 · 张三（rep）
直接输入问题，或用技能命令（如 /晨报、/会后 …）；:approve <提案id> 同意写入，:reject <提案id> 拒绝，:quit 退出
>
```

三个参数各自的理由：

| 参数 | 为什么必须带 |
|---|---|
| `-s` | 不加的话 pnpm 会先打一行 `> kaidan@0.0.0 …` 的横幅，画面上很脏 |
| `--as ou_rep_zhang` | 以销售「张三」的身份进来。演示的全部权限边界都是相对这个人说的 |
| `--now 2026-09-21T09:00:00+08:00` | **不带就没有晨报可看**。Mock 数据集里的「今天」就是 2026-09-21（周一），日程、逾期待办、临近成交日期全部挂在那一天。用真实时间跑，张三今天 0 个日程，第 1 幕直接哑火 |

### 1.3 录之前先空跑一遍

把三幕原样跑一遍再开录。两个理由：一是确认密钥没过期，二是**第一次调用往往最慢**，跑过一遍之后录出来的节奏好看。
每一幕从回车到出字大约十几秒到半分钟（评测记录里**每道任务端到端** P50 7.3 秒 / P95 19.1 秒，一幕就是一道任务）——
所以下面每一幕都配了一句「等待时说什么」，不要干等着让画面空着。

## 4. 第 3 幕 · `:approve`

### 敲什么

把第 2 幕屏幕上那两个 id 依次贴进来（**用你自己那次的 id**）：

```
:approve prop_7ad0024a-0e49-47f7-a3aa-c67cd7e038e9
:approve prop_f0660725-36fb-43a5-adc2-536077e73f4a
```

### 画面上会出现什么（2026-09-20 实跑原文）

```
> 提案 prop_7ad0024a-0e49-47f7-a3aa-c67cd7e038e9 → committed（已写入 CRM）
> 提案 prop_f0660725-36fb-43a5-adc2-536077e73f4a → committed（已写入 CRM）
```

### 嘴上说什么

> 「点一下同意，才真的写进 CRM。
>
> 产品形态里这一步是飞书卡片上的『同意』按钮——销售在手机上点一下，卡片替换成『已写入 CRM』；
> 旁边是『拒绝』，点了就是『已拒绝』，CRM 一个字不动。**飞书那一侧这周在做真机验收**，今天给你看的是同一套逻辑在命令行上跑。
>
> 每一次同意都留痕：**谁批的、什么时候批的、批了哪个提案**，都落在审计记录里。
> 而且**重复点不会重复写**——同一个提案再点一次，它只告诉你已经是 committed，不会再改一遍数据。」

### 想加个彩蛋的话（可选，会多花 30 秒）

再敲一次 `:approve` 同一个 id，屏幕上还是 `→ committed（已写入 CRM）`，数据没有被改第二遍。
这条已实测。**不确定要不要加就别加**，主线已经讲完了。

### 收尾（录屏就停在这里）

> 「三分钟，从『早上不知道今天干嘛』到『会后一句话更新完 CRM』，全程在一个聊天窗口里，销售没有打开过 CRM。
>
> 我们现在找 3 家公司做 4 周的付费试点，用你们自己的多维表格跑。有兴趣的话我们约个时间聊聊你们现在的 CRM 长什么样。」

## 5. 风险与兜底

### 5.1 模型限流 / 密钥失效

屏幕上会出现（实测原文，两行）：

```
模型服务暂时不可用，请稍后再试。
[提示] 本次运行提前结束：error
```

- **这段正文底下不会有「内容由 AI 生成」那行页脚**（2026-09-20 起改的：这句话是系统提示，不是模型写的，
  不该冒认成 AI 生成内容）。别以为是页脚丢了。
- 三句话对应三种情况（`packages/agent/src/runtime.ts` 的 `friendlyProviderError`）：
  · `模型服务当前繁忙（限流），请稍后再试。` = 百炼限流（RATE_LIMITED）；
  · `模型服务配置有误，请联系管理员检查模型配置。` = **配置本身有问题**，最常见是环境变量 `KAIDAN_LLM_API_KEY` 根本没设（CONFIG）；
  · `模型服务暂时不可用，请稍后再试。` = 其余全部走这条，**包括密钥设了但是错的 / 过期**（实测：故意用一把假密钥跑，出的就是这一句）。
- 进程**不会退出**，提示符还在，可以直接重敲上一句。

### 5.2 当场怎么圆场

| 情况 | 怎么说 | 怎么做 |
|---|---|---|
| 报「暂时不可用 / 繁忙」 | 「模型这会儿限流了，等十秒再来一次」——**不要慌着解释架构** | 原样重敲上一句。录屏的话剪掉这一段 |
| 第 2 幕没出提案（只说了一段话，底下没有「提案 prop_…」） | 「它这次只给了纪要没给提案，我再说一遍」 | **把那句话原样再发一次**。这是已知的残余风险，见 6.2 |
| 第 3 幕说「找不到该提案」 | 「id 贴错了」 | 从第 2 幕的输出里重新复制，注意别把后面的全角空格和「不要：」一起粘进来 |
| 输出里冒出 `opp_001` 这种内部 id | 不用理会，接着往下讲 | 晨报正文里已经禁掉了，提案那一行还留着（那是给管理员看的） |

### 5.3 重录的规矩

**任何一幕出岔子就整段重录，不要剪。** 三幕总共 5 分钟，重录的成本比剪出一个看得出接缝的视频低。
重录前先 `:quit` 退出、重新启动——第 3 幕的 `:approve` 已经把这个进程里的 Mock CRM 改掉了（`opp_001` 现在是 negotiation、下一步也填上了），
不退出就重跑第 2 幕，模型看到的是改完之后的数据，提案会变成一条没什么可改的空壳，甚至不出提案。

## 6. 不要吹的东西（现场被问到就照这个说）

写在这里是为了**不被问穿**。销售负责人里总有一个会问这三件事中的一件。

### 6.1 飞书真机还没验过

- 目前所有演示都在**命令行**里。飞书侧的卡片、按钮、长连接、定时晨报，**只对假的飞书测过，没在真飞书里跑过**。
- 被问到就直说：「飞书那一侧这周在验，验收清单有 12 项，验完给你看结果。」
- **千万不要说「飞书里也是这样」**——卡片长什么样、按钮点下去多久有反应，现在没人见过。

### 6.2 演示用的是虚构数据

- Mock 数据集里的公司全是编的（名字带「（虚构）」），不是任何真实客户的数据。
- 数据是**内存态**的：`:approve` 之后这个进程里的 CRM 确实变了，但**退出再进来就回到初始状态**。
  所以不要在演示里「approve 完再查一次给你看新值」——换个进程就看不到了。
  真实客户是多维表格，写进去就是写进去了，这一条只是 Mock 的性质。

### 6.3 评测成绩要怎么说

| 能说的 | 不能说的 |
|---|---|
| 「20 道题的内部评测，最近一轮 20/20；越权 0、提示词注入命中 0」 | 「准确率 100%」 |
| 「写入类任务（就是第 2 幕那种）是 12/12」 | 「不会漏提案」 |
| 「这是**单轮**成绩，这套题单轮抖动 ±2～3，要当基线还得再跑两轮」 | 装作没有抖动 |

背景（自己知道就行，不用主动讲）：同一套题当天上午还是 12/20 → 16/20，写入类只有 4/9；
下午改了技能正文之后才到 12/12 和 20/20。**所以第 2 幕仍有小概率不出提案**——这就是 5.2 那一行兜底的来历。

### 6.4 还有两处小瑕疵，别放大

- 待办的日期偶尔写成 `2026-09-23前发送…`（ISO 日期直接拼在中文里，规范是「9月23日前」）。
  被指出来就说「格式下一版收掉」，不要现场辩解。
- 提案那几行还会出现 `opp_001`、`opportunity` 这类内部标识。同上。
